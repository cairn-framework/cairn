# Map Snapshot Resync

## Problem

`map.json` is a committed, deterministic snapshot regenerated by `cairn scan`
(`dec.persistent-map-snapshot`, `src/scanner/snapshot.rs`). PR #476 changed
`src/brownfield/heuristics.rs`, `src/brownfield/discovery.rs`, and
`src/brownfield/refine.rs` but landed without the regenerated snapshot, so
`origin/main` at `cd1fc12` carried a snapshot describing the pre-#476 source.

The drift was not only shifted line ranges. The committed snapshot was missing
the `sanitised_path_derived_id` and `unique_node_id` symbol records that PR #476
added, so the graph's record of that node's surface was incomplete, not merely
offset. The line ranges also moved: `coupling_score` and `classify_score` by 36
lines, `discover` by one end line, and `run_refine` from 30-57 to 31-59.

The drift was found by the next loop iteration's preflight, which observed a
dirty `map.json` in a worktree parked at `origin/main` with no work in it. Two
consecutive `cairn scan --strict` runs from a clean checkout produce byte
identical output, so the regenerated content is the correct snapshot and the
committed one was stale.

Nothing gates this. The project gates went green on `origin/main` with the stale
snapshot, because no check compares the committed `map.json` against the one a
scan regenerates. The only reason earlier iterations in this wave stayed honest
is that each one happened to stage the file.

## Resolution

Regenerated `map.json` from `origin/main` and committed it, restoring the
snapshot to the state `cairn scan` produces.
